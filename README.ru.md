# termisations

[English](https://github.com/tzx1z/termisations/blob/main/README.md) · **Русский**

Терминальный XMPP-клиент для тех, кто отлаживает сервер, а не только переписывается.
Рядом с беседой идет панель сырого XMPP-потока, у каждого сообщения видны метки
задействованных расширений, а вся работа идет слэш-командами. Функциональный
ориентир - Conversations, отличие - плотность протокольной информации.

Клиент подключается к настоящему серверу и умеет работать на эмулированном
потоке строф: интерфейс в обоих режимах один и тот же. Интерфейс работает на
английском и русском, см. [Язык интерфейса](#язык-интерфейса).

![Беседа, панель сырого XML-потока и статус-бар](https://raw.githubusercontent.com/tzx1z/termisations/main/screenshots/overview.png)

Скриншоты сняты в эмуляторе, `termisations --mock`: адреса и сообщения на них
вымышленные. Эмулятор показывает и привязку канала, которой при подключении к
настоящему серверу пока нет, см. [Чего нет](#чего-нет).

## Установка

Из PyPI, как отдельная консольная программа:

```
uv tool install "termisations[xmpp,omemo]"
```

или

```
pipx install "termisations[xmpp,omemo]"
```

Нужен Python 3.12 или новее, клиент проверяется на Linux. Необязательные группы:

| Группа | Что добавляет |
|---|---|
| `xmpp` | `slixmpp` и `aiohttp`: подключение к настоящему серверу |
| `omemo` | `slixmpp-omemo`: шифрование OMEMO |
| `keyring` | `keyring`: пароль из системного keyring, см. [Системный keyring](#системный-keyring) |

Без групп работает только эмулятор: `termisations --mock`. С keyring:
`uv tool install "termisations[xmpp,omemo,keyring]"`. Обновление:
`uv tool upgrade termisations` или `pipx upgrade termisations`.

Из исходников, для разработки:

```
git clone https://github.com/tzx1z/termisations.git
cd termisations
uv sync --extra xmpp --extra omemo
uv run termisations --mock
```

В рабочей копии исходников все команды ниже запускаются как
`uv run termisations ...` или `.venv/bin/termisations ...`, работает и
`python -m termisations`.

## Запуск

Настоящий сервер:

```
export TERMISATIONS_PASSWORD='...'      # или --password-command 'pass show xmpp/work'
termisations --jid alice@example.org
```

`--jid` обязателен: он же выбирает профиль - каталог, в котором лежат конфиг,
история, ключи и журнал этой учетной записи. Вместо флага можно задать
переменную `TERMISATIONS_JID`. Без обоих клиент не запускается и говорит об этом:
каталог профиля нужно знать до того, как появится что читать, поэтому взять JID
из конфига нельзя.

Откуда клиент берет пароль и как его сохранить, описано в разделе
[Пароль](#пароль). Флаг `--no-history` отключает базу.

Отправка без интерфейса, для конвейера и cron:

```
termisations --jid alice@example.org --to bob@example.org --message "сборка прошла"
journalctl -u nginx -n 5 | termisations --jid alice@example.org --to bob@example.org --stdin
termisations --jid alice@example.org --to bob@example.org --file build.log --message "лог сборки"
```

В этом режиме Textual не поднимается: клиент подключается, отправляет сообщение
или файл, ждет подтверждения потоком и выходит. При успехе он молчит: пустой
вывод и код возврата 0. Код 1 означает, что подключиться или отправить не
удалось, причина уходит в стандартный поток ошибок.

База берется та же, что у интерактивного клиента с этим `--jid`, и это не деталь
реализации. В ней лежат ключи OMEMO и сохраненные беседы, поэтому шифрование в пакетном
режиме получается таким же, каким вы оставили его в этой беседе: если в
интерактивном клиенте для собеседника включен OMEMO, из конвейера сообщение
тоже уйдет зашифрованным. С `--no-history` базы нет, и клиент прямо
предупреждает, что текст уйдет открытым.

Если подключение не завершается, клиент говорит об этом сам: стадия переходит в
`error` с причиной, а не остается спиннером.

Эмулированный поток, без сети и учетной записи:

```
termisations --mock
```

Нагрузочный режим, на котором проверяется бюджет отзывчивости:

```
termisations --mock --scenario stress --rate 500
```

Флаги учетной записи: `--jid`, `--resource`, `--server` и `--port` в обход SRV,
`--direct-tls` для XEP-0368, `--no-tls-verify` для своего сервера с самоподписанным
сертификатом, `--password-command`.

Полезные флаги: `--lang {en,ru}`, `--layout {focus,split,debug}`, `--no-xml`, `--xml-buffer N`,
`--scenario {default,error,handshake,muc,stress}`, `--config PATH`,
`--log-level`. Журнал пишется в `~/.cache/termisations/<jid>/client.log`, в
терминал ничего не печатается: им владеет Textual.

## Язык интерфейса

Интерфейс работает на английском и русском: панели, статус-бар, справка команд,
ошибки, `--help`, пример конфига, переписка эмулятора и журнал `client.log`. Язык
выбирается при запуске, действует первый заданный источник:

1. флаг `--lang en` или `--lang ru`;
2. переменная `TERMISATIONS_LANG`;
3. ключ `lang` в секции `[ui]` конфига;
4. локаль системы: переменные `LANGUAGE`, `LC_ALL`, `LC_MESSAGES` и `LANG` в том
   порядке, в котором их читает gettext. Русская локаль дает русский язык, любая
   другая - английский.

```toml
[ui]
lang = "ru"
```

`/lang ru` и `/lang en` переключают язык работающего клиента до выхода, `/lang`
без аргумента показывает текущий. Строки, которые уже есть в ленте и в журнале,
остаются на языке, на котором их записали. `--help` зависит только от флага,
переменной и локали: конфиг читается после разбора аргументов. Названия стадий в
статус-баре (`resolving SRV`, `TLS handshake`, `ready`) и названия расширений -
термины протокола, на обоих языках они остаются английскими.

Переводы лежат в [`src/termisations/locale/ru/`](https://github.com/tzx1z/termisations/blob/main/src/termisations/locale/ru),
по файлу TOML на модуль: ключ - английская строка из кода, значение - русский
текст. `tests/test_i18n.py` проверяет, что у каждой строки есть перевод с теми же
подстановками и что в коде не осталось русского текста мимо каталога.

## Профили

Каждая учетная запись живет в своем каталоге. Имя каталога - bare JID в нижнем
регистре, так что `--jid Alice@Example.ORG/phone` и `--jid alice@example.org` -
один и тот же профиль.

```
~/.config/termisations/alice@example.org/config.toml
~/.local/share/termisations/alice@example.org/history.db, resource
~/.cache/termisations/alice@example.org/client.log, caps.db
```

Два аккаунта на одной машине не видят ни истории, ни бесед, ни ключей OMEMO друг
друга. Права прежние: каталоги 0700, файлы 0600. В keyring профили не нужны -
учетная запись там и так полный JID. Исключение одно: история введенных команд
общая для всех профилей, о ней ниже.

Конфиг профиля:

```toml
[account]
password_command = "pass show xmpp/work"

[tls]
verify = true
```

Если конфига в профиле нет, при запуске клиент создает пример: все настройки в
нем закомментированы и описаны, а в заголовке перечислены каталоги профиля.
Поведение клиента от примера не меняется. Чтобы включить настройку, достаточно
убрать `# ` в начале строки. Существующий конфиг не перезаписывается, а с флагом
`--config` пример не создается: настройки в этом случае лежат в другом месте. О
созданном примере клиент сообщает строкой в поток ошибок.

Ресурс по умолчанию - `termisations.<хвост>`, например `termisations.3f9a1c2e`.
Хвост случайный, создается при первом запуске профиля и хранится в файле
`resource` каталога данных профиля, как это делают Conversations и Dino. У двух
устройств одной учетной записи ресурсы не совпадают, и сервер не закрывает первую
сессию при входе второй, а у одного устройства ресурс не меняется между
запусками. `--no-history` на этот файл не влияет: это не история, а имя
устройства. Свой ресурс задается флагом `--resource` или ключом `resource` в
секции `[account]`.

Ключ `[account] jid` в профильном конфиге избыточен: учетную запись задает
каталог. Оставить его можно, но значение обязано совпадать с именем профиля -
расхождение почти всегда означает, что правят не тот файл, и клиент отказывается
запускаться. Флаг `--config PATH` перекрывает путь профиля: общий файл на
несколько учетных записей - законный способ не дублировать настройки.

Данные прежней раскладки переносятся сами. Если в корне каталогов остались
`config.toml` и `history.db` от версии без профилей, при первом запуске они
переезжают в профиль того, кому принадлежат: владельца называет `[account] jid`
из конфига, а если его там нет - единственная учетная запись в базе. Файлы чужой
учетной записи остаются на месте и дождутся своего запуска. База сразу нескольких
записей однозначного владельца не имеет и достается профилю, который запустился
первым; переписка остальных остается внутри нее, и перенести ее в их профили
можно только руками. О переносе клиент сообщает строкой в поток ошибок. Кэш и
журнал не переносятся: они восстанавливаются сами.

Эмулятору профиль не нужен: `--mock` запускается без учетной записи, в настоящую
базу не пишет и переменную `TERMISATIONS_JID` не замечает.

## Пароль

Ключа для пароля в конфиге нет: открытым текстом клиент его не хранит. Пароль
берется из внешней команды, системного keyring, переменной окружения или
запрашивается при старте. Откуда он взят в текущем сеансе, показывает команда
`/account`, строка `источник пароля`.

### Порядок источников

1. `password_command` - флаг `--password-command` или ключ `password_command` в
   секции `[account]`. Флаг важнее конфига. Если команда задана, keyring и
   переменная окружения не проверяются: когда команда завершается с ошибкой,
   остается только запрос с терминала.
2. Системный keyring. Работает, только если установлена группа `keyring`.
3. Переменная окружения `TERMISATIONS_PASSWORD`.
4. Запрос при старте. Только если стандартный ввод - терминал: в пакетном режиме
   с `--stdin`, из cron и из systemd запроса нет, клиент завершается с кодом 2 и
   пишет причину в поток ошибок. Код тот же, что у ошибки в аргументах и конфиге:
   до подключения дело не доходит.

### Какой способ выбрать

| Способ | Где хранится пароль | Подходит для | Ограничения |
|---|---|---|---|
| `secret-tool` в `password_command` | связка ключей через Secret Service: GNOME Keyring, KWallet, KeePassXC | рабочий стол Fedora и других дистрибутивов | нужны сессия D-Bus и разблокированная связка ключей: по SSH без рабочего стола и из cron не работает |
| `pass` в `password_command` | файл, зашифрованный GPG, в `~/.password-store` | терминал, в том числе по SSH; синхронизация через git | пароль от ключа GPG спрашивает pinentry; из cron работает, только пока gpg-agent помнит этот пароль |
| системный keyring, группа `keyring` | та же связка ключей Secret Service | рабочий стол без внешней команды | запись привязана к полному JID вместе с ресурсом |
| файл в `password_command` | файл с правами 0600 | cron, systemd, сервер без рабочего стола | пароль лежит на диске открытым текстом, его защищают только права файла |
| переменная `TERMISATIONS_PASSWORD` | окружение процесса | разовый запуск, CI | видна процессам того же пользователя в `/proc/<pid>/environ` |
| запрос при старте | нигде | разовый запуск в терминале | пароль вводится при каждом запуске |

### Как выполняется password_command

- Строка разбирается по правилам shell: кавычки и экранирование работают, но сам
  shell не запускается. Конвейеры, перенаправления, `~`, `$HOME` и `&&` не
  обрабатываются и уходят в команду обычными аргументами. Например, `echo pw | cat`
  без всякой ошибки отдает пароль `pw | cat`. Если нужны возможности shell,
  запускайте его явно: `sh -c 'cat "$HOME/.xmpp-password"'`. Пути пишите
  полностью: `/home/alice/...`, а не `~/...`.
- Паролем считается первая строка стандартного вывода: менеджеры паролей печатают
  пароль первой строкой, а метаданные записи ниже. Пробелы в конце строки остаются
  частью пароля.
- Команда выполняется до запуска интерфейса, поэтому может спросить пароль от
  хранилища: в том же терминале (pinentry-curses, pinentry-tty) или окном.
- На ответ отводится 30 секунд. Ошибку клиент называет прямо:
  `password_command завершилась с ошибкой: <первая строка stderr или код возврата>`,
  `password_command ничего не напечатала`, `не запустить password_command: <причина>`,
  `password_command не ответила за 30 с`.
- В интерактивном запуске при ошибке команды клиент сразу спрашивает пароль, а
  причину не показывает. Поэтому новую команду проверьте отдельно в терминале: она
  должна напечатать пароль первой строкой и завершиться с кодом 0.

### secret-tool: связка ключей Fedora

`secret-tool` входит в пакет `libsecret` и в Fedora Workstation установлен вместе
с GNOME. Пароли хранятся в связке ключей `login` GNOME Keyring, она
разблокируется при входе в сеанс. Подойдет и любая другая служба с интерфейсом
Secret Service: KWallet в KDE Plasma, KeePassXC с включенной интеграцией. Запись
определяется набором произвольных пар "атрибут значение"; пара `type xmpp`
отделяет пароли XMPP от записей других программ.

```
# Сохранить. secret-tool спросит пароль: одна строка, ввод не отображается
secret-tool store --label='XMPP JID' jid tzx1z@inkov.dev type xmpp
# Проверить: команда печатает пароль
secret-tool lookup jid tzx1z@inkov.dev type xmpp
```

Конфиг профиля `~/.config/termisations/tzx1z@inkov.dev/config.toml`:

```toml
[account]
password_command = "secret-tool lookup jid tzx1z@inkov.dev type xmpp"
```

- Ищите по тем же атрибутам, что и при сохранении. `secret-tool lookup jid
  tzx1z@inkov.dev` тоже найдет запись, но если другая программа сохранила запись
  с таким же атрибутом `jid`, secret-tool вернет первую разблокированную из
  подходящих.
- Повторный `store` с теми же атрибутами заменяет пароль в существующей записи,
  новая запись не создается. Так пароль обновляется после смены на сервере.
- Удалить запись: `secret-tool clear jid tzx1z@inkov.dev type xmpp`. Запись видна
  в приложении "Пароли и ключи" (Seahorse) под меткой из `--label`.
- Пароль можно передать `store` через стандартный ввод, но перевод строки в конце
  тогда сохраняется как часть пароля. Клиенту он не мешает, потому что берется
  первая строка, а другим программам может помешать. Пароль, набранный в самой
  команде, остается в истории shell, поэтому удобнее ввод по запросу.
- Если записи нет, `secret-tool` завершается с кодом 1 без сообщения, и клиент
  пишет `password_command завершилась с ошибкой: код возврата 1`.
- Если связка ключей заблокирована, GNOME Keyring показывает окно с запросом
  пароля от нее.
- Из cron secret-tool не находит сессию D-Bus и пишет
  `secret-tool: Cannot autolaunch D-Bus without X11 $DISPLAY`. По SSH шина
  обычно есть (systemd поднимает ее при входе), но связка ключей `login`
  разблокируется входом в графический сеанс: если такого сеанса на машине нет,
  запись не читается. Для таких запусков подходит файл с паролем, а команду из
  конфига перекрывает флаг `--password-command`.

### pass

```
sudo dnf install pass
# Один раз: ключ GPG и хранилище. <GPG_ID> - адрес или отпечаток ключа
gpg --full-generate-key
pass init <GPG_ID>
# Сохранить: pass спросит пароль дважды
pass insert xmpp/example.org
# Проверить
pass show xmpp/example.org
```

```toml
[account]
password_command = "pass show xmpp/example.org"
```

- Запись хранится в `~/.password-store/xmpp/example.org.gpg`. Имя записи
  произвольное; для нескольких учетных записей удобно называть записи по JID:
  `xmpp/tzx1z@inkov.dev`.
- `pass insert -m` принимает несколько строк: пароль первой строкой, ниже
  метаданные. Клиент берет только первую строку.
- Пароль от ключа GPG спрашивает pinentry через gpg-agent: окном на рабочем столе
  или в терминале. gpg-agent помнит его 10 минут после последнего использования
  (`default-cache-ttl`) и не дольше 2 часов (`max-cache-ttl`). Из cron pinentry
  показать некуда: команда работает, только пока пароль в кэше gpg-agent, иначе
  завершается ошибкой или по таймауту через 30 секунд.

### Системный keyring

Клиент читает пароль из keyring сам, без внешней команды. Нужна группа `keyring`:

```
uv tool install "termisations[xmpp,omemo,keyring]"
# или в рабочей копии исходников
uv sync --extra xmpp --extra omemo --extra keyring
```

Запись ищется в службе `termisations`, имя записи - полный JID вместе с ресурсом,
например `alice@example.org/termisations.3f9a1c2e`. Ресурс профиля хранится в
файле `resource` каталога данных профиля, файл появляется при первом запуске.
Полный JID показывает и `/account`, строка `учетная запись`.

```
JID="alice@example.org/$(cat ~/.local/share/termisations/alice@example.org/resource)"
# Сохранить через CLI библиотеки keyring: он спросит пароль
uv run keyring set termisations "$JID"
# Проверить
uv run keyring get termisations "$JID"
```

Бэкенд SecretService библиотеки keyring ищет запись по атрибутам `service` и
`username`, поэтому ту же запись можно создать через secret-tool. На Linux этот
бэкенд выбирается по умолчанию. Бэкенд libsecret ищет еще и по атрибуту
`application`, и запись из secret-tool он не найдет:

```
secret-tool store --label="termisations $JID" service termisations username "$JID"
```

- Если ресурс меняется (флаг `--resource`, ключ `resource` в конфиге, удаленный
  файл `resource`), запись со старым именем не находится. Сохраните пароль под
  новым полным JID.
- Ошибку keyring клиент считает отсутствием пароля и переходит к следующему
  источнику: без сессии D-Bus или с заблокированной связкой ключей (cron, SSH
  без графического сеанса) keyring пропускается без сообщения.
  Выбранный бэкенд показывает
  `uv run python -c "import keyring; print(keyring.get_keyring())"`, на рабочем
  столе Fedora это `keyring.backends.SecretService.Keyring`.

### Файл с паролем: cron и сервер без рабочего стола

```
# Файл с правами 0600 в каталоге конфига профиля. printf - встроенная команда
# bash, поэтому пароль не попадает ни в историю, ни в список процессов
(umask 077; read -rs -p 'Пароль: ' pw; echo; printf '%s\n' "$pw" > ~/.config/termisations/alice@example.org/password)
```

В `password_command` путь указывается полностью, `~` не раскрывается. Если в
конфиге уже стоит команда для рабочего стола, в задании cron ее перекрывает флаг:

```
termisations --jid alice@example.org \
  --password-command 'cat /home/alice/.config/termisations/alice@example.org/password' \
  --to bob@example.org --message "сборка прошла"
```

Пароль в таком файле защищают только права доступа, и он попадает в резервные
копии домашнего каталога. Для автоматических отправок надежнее завести отдельную
учетную запись, чтобы утечка файла не открывала личную.

### Переменная TERMISATIONS_PASSWORD

- Не пишите пароль в команде `export`: строка останется в истории shell. Вариант
  для bash без истории: `read -rs TERMISATIONS_PASSWORD && export TERMISATIONS_PASSWORD`.
- Переменную видят все дочерние процессы, а также процессы того же пользователя
  через `/proc/<pid>/environ`. Для постоянного использования надежнее способы
  выше.
- Переменная действует, только если `password_command` не задана ни флагом, ни в
  конфиге, а в keyring записи нет.

### Запрос при старте

Если ни один источник не дал пароль и стандартный ввод - терминал, клиент до
запуска интерфейса спрашивает `пароль для <полный JID>:`. Пароль нигде не
сохраняется, пустой ввод отменяет запуск.

## Что на экране

Сверху две панели: беседа с метками расширений и панель `RAW XML` со строками вида
`12:04:11.238 OUT iq ...`. Ниже строка ввода с подсказкой сигнатуры, внизу
статус-бар в две строки: JID, шифрование канала и беседы, задержка, транспорт,
состояние XEP-0198, память, спиннер текущей стадии.

Вывод команд идет в беседу, здесь `/sm` и `/caps bob@example.org`:

![Вывод /sm и /caps в беседе](https://raw.githubusercontent.com/tzx1z/termisations/main/screenshots/commands.png)

Мок проигрывает подключение целиком: резолв SRV, TLS-хендшейк, SASL2 с
маскированной полезной нагрузкой, bind, `<enable/>` по XEP-0198, запрос roster,
начальные presence, пачку MAM, бандл ключей OMEMO из PEP, входящее зашифрованное
сообщение, отправку receipt, маркер, корректировку и строфу `type='error'`.

Клавиши приложения: Ctrl+D - цикл раскладок, Ctrl+P - палитра команд, Ctrl+O -
палитра контактов, Ctrl+R - поиск по истории ввода, Alt+1..9 - беседа по номеру,
Ctrl+N и Ctrl+B - соседние беседы, Ctrl+L - очистка лога, Ctrl+F - фильтр,
End - вернуться к концу потока, Esc - сброс, Ctrl+C - копирование выделенного
или выход с подтверждением, а второе нажатие подряд закрывает клиент сразу.
Диалог выхода отвечает и на кириллице: д - выйти, н - остаться.

Раскладка `debug`, Ctrl+D или `/debug`: сырой поток на всю ширину.

![Раскладка debug: сырой XML-поток на всю ширину](https://raw.githubusercontent.com/tzx1z/termisations/main/screenshots/debug.png)

Все сочетания с Ctrl работают на любой раскладке. Терминал с расширенным
протоколом клавиатуры передает символ вместе с модификатором, а не управляющий
код, поэтому на русской раскладке приходит Ctrl+С вместо Ctrl+C. Двойники для
всех сочетаний заводятся списком в `app.with_cyrillic`, включая вариант с
включенным Caps Lock. Если сочетание все равно не срабатывает, посмотрите, что
приходит от вашего терминала: `.venv/bin/textual keys`.

Палитра контактов устроена как палитра команд: тот же нечеткий поиск, выбор
переключает беседу. Записи сгруппированы по серверу, домен показан у первой
записи группы, внутри группы доступные контакты идут раньше отключенных.
Комнаты в контакт-листе не хранятся, но в палитру попадают: перейти в них
нужно так же.

Строка ввода: Tab дополняет команды, JID и ники, Up и Down листают историю,
Alt+Enter и Ctrl+J переносят строку, Backspace возвращает предыдущую строку
многострочного ввода. Вставка из буфера идет всеми строками: текст с переводами
раскладывается по тому же буферу, что и Alt+Enter, и уходит одним сообщением.

Панель RAW XML: Shift+Tab переводит на нее фокус и обратно, стрелки двигают
курсор по строфам, Enter разворачивает строфу под курсором, End возвращает поток,
PgUp и PgDn листают страницами. Полная таблица - команда `/keys`.

Фильтр панели лога: `kind:<тип> jid:<адрес> ns:<пространство> err:<да|нет>` и
свободный текст, условия объединяются по И. Типы строф: `msg`, `pres`, `iq`,
`strm`, `sasl`, `tls`, `oth`. Пример: `/xml filter kind:iq ns:urn:xmpp:mam:2`.
Неизвестное поле или значение команда не применяет, а объясняет; в ответе видно,
сколько строф буфера подошло под условия. Tab после `/xml filter` подставляет
имена полей, в том числе для второго и третьего условия.

## История ввода

Введенные команды переживают перезапуск и общие для всех профилей. Стрелка вверх
поднимает то, что набиралось и вчера, и в другой учетной записи, Ctrl+R открывает
обратный поиск по истории, как в bash: поле ввода становится строкой запроса,
найденная команда стоит в подсказке под ним. Повторный Ctrl+R уходит к следующему
совпадению вглубь, Enter кладет найденное в поле, Escape и Ctrl+G отменяют поиск и
возвращают набранный текст. Enter в поиске ничего не отправляет: в реестре есть
`/quit`, `/send` и `/remove`.

```
~/.local/share/termisations/input-history.db
```

Файл один на все профили и лежит рядом с их каталогами: набранная команда
принадлежит человеку, а не учетной записи, и второй аккаунт не должен начинать с
пустой истории. Права те же, что у остальных данных: каталог 0700, файл 0600.
Хранятся последние 5000 строк.

В файл идут только слэш-команды. Тексты сообщений в него не попадают: профили
заведены затем, чтобы переписка одной учетной записи не оказалась в данных
другой. Стрелка вверх в текущем сеансе по-прежнему поднимает и отправленные
сообщения, но на диск они не пишутся.

В командах есть адреса - `/chat`, `/join`, `/mam`, `/block`, - и по общему
файлу видно, с кем шла переписка в других профилях. Это цена общей
истории. Маскирование к записям не применяется: замаскированную команду нельзя
повторить, а повтор - вся польза истории.

Эмулятор историю читает, но не пишет: `--mock` не оставляет следов на диске и
файла истории не создает. Флаг `--no-history` отключает и базу переписки, и
запись ввода. Ответы на вопросы подтверждения (`yes`, `да`) в историю не идут.

## Что работает

- Подключение к серверу: резолв SRV `_xmpps-client._tcp` и `_xmpp-client._tcp`
  с учетом приоритета и веса, прямой TLS по XEP-0368 или STARTTLS, SASL со
  SCRAM-SHA-256 и SCRAM-SHA-512, привязка ресурса.
- Расширения на реальном потоке: XEP-0198 с подтверждениями, XEP-0199 как
  источник задержки, XEP-0030 и XEP-0115, XEP-0280 Carbons, XEP-0313 MAM
  с постраничной выборкой, XEP-0359, XEP-0184, XEP-0333, XEP-0308, XEP-0085.
- Панель сырого потока показывает строфы такими, какими они прошли по сокету:
  перехват стоит на уровне сокета, а не на разобранных объектах.
- Три режима раскладки и адаптация к ширине терминала: от 160 колонок лог справа,
  от 80 - снизу, ниже 80 лог скрывается с уведомлением.
- Панель сырого потока: кольцевой буфер на 2000 строф, батч-рендер не чаще 20 раз
  в секунду, подсветка разметки, разворот строфы по Enter, follow и pause со
  счетчиком непоказанных строф, фильтр по типу строфы, адресу и пространству имен,
  частота потока в заголовке.
- Панель беседы показывает историю беседы, а не журнал сессии: транспортные
  события (пинги, подтверждения потока, TLS, SASL, disco) идут в панель лога и в
  статус-бар, состояние набора текста - в строку заголовка беседы с затуханием,
  а в ленте остаются сообщения и относящиеся к ним события.
- Итог каждой стадии подключения с длительностью печатается сводкой в беседе:
  DNS, TLS, SASL, bind, SM, roster, presence, MAM и общее время.
- Маскирование секретов по умолчанию: SASL, ключи и тела OMEMO, бандлы PEP, пароли
  комнат, подписи в ссылках XEP-0363. Полный вид включается только `/xml --unsafe`
  с подтверждением вводом, пока он активен горит маркер `UNSAFE`.
- 45 слэш-команд из одного реестра-данных: справка, автодополнение и палитра
  строятся из него автоматически.
- `/log save <файл>`: запись буфера с текущим маскированием, файл создается с
  правами 0600, открытие с `O_NOFOLLOW`.
- История введенных команд между запусками, общая для всех профилей: стрелка
  вверх и обратный поиск по Ctrl+R, файл с правами 0600 на последние 5000 строк.
- Метки расширений в беседе формируются из таблицы `xeps.py`, а не из строк в UI.
  Расширения, срабатывающие на каждом сообщении, свернуты в знаки `#`, `✓`, `⇢`,
  `↑` в строке сообщения, расшифровка в `/keys`. Полный вид остается в панели
  сырого потока и в выводе `/trace`.

## Чего нет

- Проверенного живьем SASL2. Адаптер SASL2 и Bind 2 написан
  (`protocol/sasl2/`) и проверен на строфах, но сервера с поддержкой под рукой
  нет: в ejabberd 26.7.0 из тестового контейнера модулей `mod_sasl2` и
  `mod_bind2` нет, возможность не объявляется. Работает запасной путь SASL1, и он
  проверен живыми тестами. Отключить попытку SASL2 можно ключом
  `[account] sasl2 = false` или флагом `--no-sasl2`.
- Привязки канала (XEP-0440) и SCRAM-PLUS: в стандартном `ssl` реализован только
  `tls-unique`, запрещенный на TLS 1.3 (RFC 9266), а `tls-exporter` в CPython
  отсутствует. Поле привязки показывает `n/a`, а не выдуманное значение.
- OMEMO в пространстве имен `urn:xmpp:omemo:2`. Работает
  `eu.siacs.conversations.axolotl`: в slixmpp-omemo 2.2.0 подготовка открытого
  текста для omemo:2 не реализована, а расшифровка входящего omemo:2 поднимает
  `NotImplementedError`. Бандлы публикуются в обоих пространствах имен, потому
  что это делает сама библиотека; `/omemo status` называет рабочее.
- OX (XEP-0373): поддерживаемой реализации для Python нет, команда отвечает
  прямо. В режиме `--mock` она показывает разметку события.
- Аватаров XEP-0084: показывать картинку в терминале нечем, а текстовая метка
  требует отдельного решения о виде.
- Доставки отзыва там, где сервер ее не делает: `/retract` собирает и
  отправляет строфу `urn:xmpp:message-retract:1`, но ejabberd 26.7.0 не
  пересылает ее другим ресурсам, хотя расширение в своих возможностях
  объявляет. Реакция по XEP-0444 при тех же условиях доходит.
- Шифрования сообщений самому себе: круг OMEMO проверен между двумя учетными
  записями, а сценарий заметок себе в ленте не проверялся.

### Живые тесты

Тесты с маркером `live` работают с настоящим XMPP-сервером и пропускаются, если
он недоступен:

```
.venv/bin/pytest -m live
```

По умолчанию нужен сервер на `127.0.0.1:5222` с доменом `localhost`, учетные
записи `alice` и `bob` с паролями `S3cr3t-<user>-2026` и комната
`devops@conference.localhost`. У двух учетных записей должны быть взаимные
подписки (`ejabberdctl add_rosteritem` в обе стороны): без них OMEMO не забирает
списки устройств из PEP, и сценарии шифрования не проходят.

Переменные `TERMISATIONS_TEST_HOST`, `TERMISATIONS_TEST_PORT`,
`TERMISATIONS_TEST_DOMAIN`, `TERMISATIONS_TEST_USER`, `TERMISATIONS_TEST_PEER`,
`TERMISATIONS_TEST_ROOM` и `TERMISATIONS_TEST_PASSWORD` заменяют значения по
умолчанию. На публичном сервере с одной учетной записью собеседником выступает
вторая сессия того же пользователя:

```
TERMISATIONS_TEST_HOST=xmpp.example.org TERMISATIONS_TEST_DOMAIN=example.org \
TERMISATIONS_TEST_USER=<логин> TERMISATIONS_TEST_PEER=<тот же логин> \
TERMISATIONS_TEST_ROOM=<комната>@chat.example.org \
TERMISATIONS_TEST_PASSWORD=<пароль> \
.venv/bin/pytest -m live
```

Хост задается отдельно от домена: у публичных серверов A-запись домена часто
ведет на CDN, а XMPP слушает на своем имени. Сценарии, которым нужен второй
участник, - маркер прочтения и круг OMEMO - на таком профиле пропускаются с
названной причиной.

Ключи OMEMO живых тестов лежат в `termisations-live-omemo/` во временном каталоге
системы и сохраняются между прогонами. Каждая новая база ключей публикует в PEP
новое устройство, а старые устройства там остаются, поэтому новая база на каждом
прогоне со временем оставила бы собеседника без пригодного устройства. Начать с
нуля - удалить каталог и снять списки устройств на сервере.
